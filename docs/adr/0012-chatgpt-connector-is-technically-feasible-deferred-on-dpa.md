# ChatGPT MCP connector is technically feasible; deferred as a committed v1 client on the data-handling precondition

The ChatGPT connector spike resolves **GO on the connector, NO-GO on committing ChatGPT as a v1 client**. Claude stays the sole committed v1 client; ChatGPT is validated-feasible-but-deferred, gated by the [0011](0011-mcp-server-is-public-and-accepts-redacted-data-egress.md) data-handling precondition (a zero-retention / no-train DPA covering egress to OpenAI's cloud), **not** by any connector gap. This finalizes the client list [0009](0009-mcp-server-replaces-staff-copilot-chat-ui.md) and [0010](0010-mcp-access-is-per-user-oauth-impersonation.md) left to a spike. The spike measured no blocking gap — every OAuth 2.0 discovery requirement a ChatGPT custom connector needs is already emitted by the pinned `laravel/mcp` build, so the "small metadata fixes" branch is empty by verification. The measured evidence and the reproduction steps live with the task in `.scratch/swinx-mcp-server/issues/07-chatgpt-connector-spike.md` and are locked by `tests/Feature/Mcp/McpChatGptConnectorSpikeTest.php`.

Two residuals are accepted for v1, both matching the Claude path: tokens are **not** audience-bound to the RFC 8707 `resource` parameter (Passport ignores it; tightening needs its own ADR), and consumer-plan blocking is best-effort (a resource server cannot enforce the caller's provider plan tier). Because the block is the DPA and not engineering, committing ChatGPT later is a documentation-and-DPA step, not a code change.
