# Canvas Integration Contract

## Purpose

This document defines where the Canvas integration is configured and the
constraints that operators must know before mapping or syncing a course.
Day-to-day sync steps and recovery are in
`docs/features/canvas/operations.md`.

## Integration boundary

Swinx currently treats Canvas as one shared installation across campuses.
Canvas credentials are stored in `canvas_integrations`; course discovery rows
and local mappings are stored in `canvas_course_mappings`. The active
integration is selected globally, while the local course-offering choices shown
to an operator are scoped to the selected campus.

Executable owners:

- `app/Models/CanvasIntegration.php`
- `app/Models/CanvasCourseMapping.php`
- `app/Services/Canvas/CanvasApiService.php`
- `app/Services/Canvas/CanvasTokenService.php`
- `app/Services/Canvas/CanvasSyncService.php`
- `routes/web/canvas.php`

Client secrets, access tokens, and refresh tokens are encrypted by the
`CanvasIntegration` model and hidden from serialization. OAuth state is stored
in the staff session and checked on callback.

## Canvas developer key

Create an OAuth developer key in the Canvas instance with the callback URL
generated by the named route:

```text
https://<swinx-domain>/admin/canvas/oauth/callback
```

The public scheme and host come from Laravel URL generation, so `APP_URL` and
reverse-proxy forwarding must be correct before authorizing.

Application-wide Canvas options are limited to:

```env
CANVAS_DEFAULT_SCOPES=""
CANVAS_API_TIMEOUT=30
```

Their owner is the `canvas` section of `config/services.php`. The Canvas URL,
client ID, and client secret are entered in the admin integration page rather
than stored in those environment variables.

## Admin setup

1. Open the Canvas integrations page
   (`admin.canvas.integrations.index`).
2. Create the integration with the Canvas base URL and developer-key
   credentials.
3. Authorize it through Canvas OAuth.
4. Sync the Canvas course catalog.
5. Open the Canvas courses page and map each required Canvas course to exactly
   one local course offering.

Route permissions are declared in `routes/web/canvas.php` and
`config/permission.php`. Integration creation, editing, deletion, course sync,
and course mapping use distinct permissions; do not replace them with a broad
Canvas-admin check.

## Mapping and syllabus ownership

A Canvas course mapping points to a local `CourseOffering`. Assignment sync
requires that offering to already have a syllabus template.

On the first assignment sync, Swinx clones that template for the offering and
marks the offering as Canvas-synced. Subsequent assignment syncs reuse the
cloned template. This avoids mutating a template that may be shared by another
offering.

Selected Canvas assignment groups must total 100 percent. When selected groups
are applied, `CanvasAssignmentSyncService` removes the cloned template's
existing assessment components and recreates them from the selected Canvas
groups. This is a destructive replacement of local component structure, not a
merge. Review the sync summary and selection before applying.

The exact behavior is owned by:

- `app/Services/Canvas/CanvasAssignmentSyncService.php`
- `tests/Feature/CourseOffering/CanvasSyllabusTemplateGuardTest.php`

## Grade identity and authority

Students are matched to Canvas by uppercased local student code against Canvas
`sis_user_id`, with `login_id` as a fallback. An unmatched student is skipped
and reported; Swinx does not guess by name or email.

Canvas assignment submissions update local detail scores. A default-weighted
syllabus may also consume the Canvas course total. A custom grading engine
remains authoritative over the final result; see
`docs/features/academic/grading.md`.

The current grade-sync owner is
`app/Modules/Academic/Delivery/Support/CanvasGradeSyncService.php`.
